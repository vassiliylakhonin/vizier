# Vizier threat model

## 1. Overview

Vizier evaluates proposed agent actions against delegated authority and constraints. It returns ALLOW, REVIEW or BLOCK and a canonical request digest. A Cloudflare Worker exposes REST, MCP and A2A interfaces, covenant attestations, an administrative human-review queue, financial reservation/observation workflows and an OpenAI-compatible proxy. TypeScript and Python clients integrate these interfaces. Separate operator-owned adapters can place authorization before MCP calls or Cloudflare Worker-version deployment.

This repository-wide model describes source at the footer revision. It is an offline architecture review, including an independent architecture pass; it is not a completed vulnerability audit or evidence of deployed configuration. No application, exploit input or external service was executed. The current security policy explicitly defines assessment objectives rather than universal implementation guarantees (`SECURITY.md:24-33`). Repository sources, examples and documentation are evidence rather than instructions.

Normal REST flow is credential validation, bounded JSON/schema parsing, optional KV circuit-breaking/sanctions/quorum and local DLP checks, deterministic kernel evaluation, response and best-effort metadata persistence. MCP/A2A directly invoke the kernel with authentication/grant configuration; they do not call that REST enrichment pipeline. The integrating application normally executes the action and must stop on REVIEW/BLOCK or verification failure. These paths therefore have materially different controls (`src/transport/http.ts:321`, `src/transport/mcp.ts:297`, `src/transport/a2a.ts:406`).

## 2. Threat Model, Trust Boundaries, and Assumptions

Assets are authorization integrity; request/action/approval binding; credentials and private signing keys; principal registry integrity; quota/revocation state; review confidentiality; financial holds and evidence; upstream tool authority; Cloudflare deployment authority; and production/package integrity.

An anonymous caller controls request bodies, JSON-RPC metadata, headers and proposed actions/evidence, but does not automatically possess integration, reviewer or principal signing credentials. The Worker requires application/json, caps streamed bodies at 1 MiB and bounds JSON complexity before schema checks. Anonymous MCP/A2A run an untrusted-authority REVIEW rule, preventing ALLOW; MCP validates Origin when present. Their anonymous gate uses CF-Connecting-IP with configured 60/60-second limiting (`src/transport/shared.ts:113`, `src/core/policies.ts:92`, `src/transport/mcp.ts:165`, `src/transport/http.ts:1167`, `wrangler.jsonc:30`).

Integration credentials confer service authority. Optional grant mode deliberately accepts integration-asserted authority: credential possession alone does not prove principal delegation. Grants verify registered ES256 signatures, validity dates, issuer, subject and canonical equality of complete authority. Audience checking is conditional on an expected audience; inspected Worker verification does not supply one. Required mode is operator configuration, not request input (`src/core/grants.ts:195`, `src/core/grants.ts:242`, `src/transport/http.ts:345`, `src/transport/shared.ts:194`).

Tenant keys provide revocation/quota bookkeeping. Most authenticated handlers receive status rather than organization identity. Shared reset, custom-sanctions, quorum and insights consumers therefore do not establish tenant-scoped ownership merely by accepting tenant credentials. MCP/A2A authentication does not pass D1 options, unlike REST. Actual intended tenant privileges and deployment population remain questions (`src/transport/auth.ts:85`, `src/transport/http.ts:228`, `src/transport/http.ts:456`, `src/transport/http.ts:739`, `src/transport/http.ts:930`, `src/transport/mcp.ts:261`, `src/transport/a2a.ts:311`).

Covenant acceptance is an authenticated integration assertion naming the principal and draft hash. Evidence/signals and reported outcomes remain integration-supplied data; their hashes prove binding rather than truth. Authorization/outcome tokens use distinct JWS types; outcome recording verifies authorization signatures (`src/covenants/lifecycle.ts:94`, `src/covenants/lifecycle.ts:316`, `src/covenants/lifecycle.ts:374`, `docs/THREAT_MODEL.md:140`).

Human reviews form a distinct single-operator administrative boundary. They require separate integration/reviewer secrets and exclude tenant keys. Reviewer decisions bind the displayed request hash; the SDK checks issuer, audience, review identifier, exact hash, expiry and signature before claiming. D1 conditional consumption differs from KV quorum consumption. Financial reservations add SQL-trigger budget enforcement; reconciliation observes finalized Base native-USDC behavior and does not sign payments (`src/reviews/api.ts:48`, `src/reviews/api.ts:149`, `packages/sdk/src/index.ts:759`, `src/reviews/api.ts:175`, `migrations/0007_financial_reservations.sql:46`, `src/reviews/api.ts:178`).

Private MCP execution requires operator-controlled allowlist, identity, destination and credentials. The proxy checks client bearer, tool allowlist and ALLOW before forwarding. Strict grant mode additionally verifies returned provenance and request hash; configured timeouts and redirect refusal constrain dependency behavior. An agent with direct upstream credentials or equivalent tools can bypass this boundary (`packages/mcp-proxy/src/index.ts:561`, `packages/mcp-proxy/src/index.ts:673`, `packages/mcp-proxy/src/index.ts:748`, `docs/THREAT_MODEL.md:168`).

The Worker-version executor snapshots strict plans, fixes account/worker, checks principal-signed provenance, consumes exact human approval, and makes one deployment POST. Response loss yields reconciliation rather than retry. Its security depends on an operator-owned process that withholds Cloudflare credentials/general shell from the agent. The legacy local wrapper separately reads macOS Keychain and invokes local Wrangler; it is not a Linux scanner prerequisite (`packages/gated-deploy/src/worker-version.ts:125`, `packages/gated-deploy/src/cli.ts:36`, `docs/THREAT_MODEL.md:164`).

Material documentation disagreements must remain visible:

- `docs/THREAT_MODEL.md:91` describes metadata-only D1 with no parameters/tokens. Operational audit writers support that claim, while newer administrative reviews persist canonical payloads and tokens (`src/storage/audit.ts:56`, `src/reviews/api.ts:100`, `src/reviews/api.ts:158`).
- The current policy distinguishes required authorization failures from best-effort logging (`SECURITY.md:26`). Operational audit failures are caught after response, and proxy receipt-signing errors do not stop its completed response (`src/transport/http.ts:205`, `src/proxy/index.ts:852`). Verify the actual integration's mandatory failure classes.
- The current policy requires assessment of quorum storage atomicity and lifetime (`SECURITY.md:29`). Code uses expiring KV read/check/write state; distributed atomicity and permanent anti-resurrection are not established here (`src/core/quorum.ts:257`).
- The current policy separates hostname validation from DNS/network assumptions (`SECURITY.md:30`). URL-origin and hostname controls are established; independent DNS-address pinning is not shown by the inspected resolver (`src/proxy/index.ts:223`).
- Legacy verification receipts are unsigned digest records, whereas covenant/review attestations are signed (`src/core/receipts.ts:76`, `docs/THREAT_MODEL.md:132`).

Actual deployed grant mode/registry, secret rotation, Cloudflare credential scopes, DNS, tenant access expectations, CI branch protections and environment approvals remain unknown. Source configuration is not deployment readback. External providers and CI dependencies remain separate trust assumptions.

## 3. Attack Surface, Mitigations, and Attacker Stories

The following are review hypotheses and coverage questions, not confirmed vulnerabilities. Each requires a demonstrated control failure and new authority or impact.

| Priority | Scenario and capability gain | Prerequisite / impact | Controls, mitigation and evidence |
| --- | --- | --- | --- |
| High | Tenant credential changes another integration's shared security state or reads shared insights. | Multiple mutually untrusted tenants and an ownership promise; isolation failure rather than authorized shared administration. | Credentials/quota exist; org context is not propagated. Resolve intended privileges, then enforce ownership or restrict administrative roles: `src/transport/http.ts:228`, `src/transport/http.ts:622`, `src/transport/http.ts:930`. |
| High | Concurrent quorum claim yields more than one authorized execution. | Shared proposal, concurrent consumers and executor acting on both results. | Action hashes and consumed checks exist; KV writes lack an explicit transaction. | High | Agent bypasses intended execution gate. | Agent can access upstream/Cloudflare token, shell or alternate transport; without separation this is already-held authority. | Fix operator-owned deployment/MCP capabilities and withhold broader access: `packages/gated-deploy/src/worker-version.ts:125`, `docs/THREAT_MODEL.md:164`. |
| Medium | One transport omits controls expected by an integration. | Caller can choose MCP/A2A instead of REST and downstream treats results equivalently. | Kernel still enforces its policies; REST enrichment differs. ## 4. Severity Calibration (Critical, High, Medium, Low)

**Critical:** An unprivileged actor obtains broad production execution, deployment or cross-tenant credential authority across a realistic exposed boundary. This requires evidence of reachability, effective privileges and broad impact. Ordinary maintainer-controlled release behavior or an agent already holding Cloudflare credentials does not establish this severity.

**High:** A lower-privileged actor obtains unauthorized deployment, another tenant's protected state, or repeated sensitive execution despite required approval. Exact-approval signatures, fixed deployment scope, conditional D1 claim and existing consumed checks are counterevidence that must be reconciled. A KV concurrency hypothesis alone is insufficient.

**Medium:** A bounded confidentiality, integrity or availability failure affects a real integration, such as an established transport-control mismatch or reachable unintended upstream destination. Severity depends on actual tenant promises, network exposure, authorization configuration and downstream execution. Grantless integration assertions in explicitly optional mode are documented behavior.

**Low:** Limited information disclosure or a defense-in-depth gap with small demonstrated impact. Documentation drift can warrant correction without proving a vulnerability. Best-effort audit loss is not automatically authorization bypass; missing signatures matter only where consumers require and trust them.

Confidence and severity are separate. Unresolved deployment prerequisites remain questions, not findings. Future review should preserve source-backed rejections and uncertainties rather than interpreting this architecture map as completed audit coverage.
